ERROR: Jenkins not starting after installation
CAUSE: Port 8080 already in use or Java not configured properly.
SOLUTION:
- Check if port 8080 is free: `netstat -ano | findstr 8080`
- Kill process or change Jenkins port in `jenkins.xml` or `jenkins.yml`
- Ensure JAVA_HOME is set correctly.

ERROR: No valid crumb was included in the request
CAUSE: CSRF protection enabled and crumb missing.
SOLUTION:
- Add Jenkins-Crumb header in API requests.
- Use `curl -u user:token http://localhost:8080/crumbIssuer/api/json` to get crumb.

ERROR: Jenkins build stuck in the queue
CAUSE: No executors available or node offline.
SOLUTION:
- Check node status in Manage Jenkins > Nodes.
- Increase executor count in node configuration.
- Restart Jenkins service.


ERROR: OutOfMemoryError: Java heap space
SOLUTION:
- The `OutOfMemoryError: Java heap space` error means your Java application has run out of memory in the heap.  The heap is where Java objects are allocated. This error is a common problem, and the solution depends on its root cause. Here's a breakdown of how to troubleshoot and resolve it:
- 
- **1. Identify the Cause:**
- 
- The most crucial step is to find *why* your application is consuming so much memory.  This often requires profiling and careful examination of your code.  Here are some common culprits:
- 
- * **Memory Leaks:** This is the most frequent cause.  A memory leak occurs when objects are no longer needed but are still referenced, preventing the garbage collector from reclaiming the memory.  Common scenarios include:
-     * **Unclosed resources:**  Forgetting to close `InputStreams`, `OutputStreams`, `Files`, database connections, etc.  These often hold onto significant memory.
-     * **Static collections:**  Large static collections that grow indefinitely without proper cleanup.
-     * **Unreachable objects:**  Objects that are accessible through a complex chain of references, but ultimately no longer used by the application's main logic.
-     * **Circular references:** Objects referencing each other, creating cycles that the garbage collector struggles to resolve.  Often happens with complex object graphs.
- 
- * **Large Datasets:** Your application might be processing datasets that are simply too large to fit within the available heap space.
- 
- * **Inefficient Algorithms:** Algorithms with high memory complexity (e.g., O(n^2) or O(2^n)) can consume excessive memory as the input size grows.
- 
- * **Insufficient Heap Size:** Your JVM might simply not have been allocated enough memory to begin with.
- 
- * **Third-party Libraries:** A bug or inefficient implementation within a third-party library you're using.
- 
- **2. Debugging Techniques:**
- 
- * **Heap Dumps:** Take a heap dump (using tools like JConsole, VisualVM, or MAT – Memory Analyzer Tool) to analyze the memory usage at the time of the error. This provides a snapshot of all objects in the heap, allowing you to identify objects consuming significant memory and track down memory leaks.
- 
- * **Profiling Tools:** Use Java profiling tools (like JProfiler, YourKit, or Java VisualVM's profiler) to monitor memory usage *during* runtime. This helps identify which parts of your code are consuming the most memory and pinpoint leaks in real-time.
- 
- * **Logging:** Add logging statements to track object creation and destruction to help spot unusual patterns in memory usage.
- 
- * **Code Review:** Carefully review your code, paying close attention to resource management (closing resources), the use of static variables, and the creation and lifetime of objects.  Look for areas where objects might be held onto longer than necessary.
- 
- 
- **3. Solutions:**
- 
- Once you've identified the cause, the solution will vary:
- 
- * **Fix Memory Leaks:**  This requires careful code review and debugging to eliminate the root causes of memory leaks.  Use the debugging techniques mentioned above.
- 
- * **Optimize Algorithms:**  If the issue is algorithmic complexity, consider using more efficient algorithms or data structures to reduce memory usage.
- 
- * **Increase Heap Size (Temporary Fix):**  You can increase the heap size allocated to the JVM using the `-Xmx` and `-Xms` flags when starting your application.  For example: `java -Xmx4g -Xms4g MyApplication`.  `-Xmx` sets the maximum heap size, and `-Xms` sets the initial heap size.  **This is a band-aid, not a cure.** It only postpones the problem; you still need to address the underlying memory leak or inefficiency.
- 
- * **Off-Heap Memory:** For very large datasets that can't fit in the heap, consider using off-heap memory solutions (like memory-mapped files) to store data outside the JVM's heap.  This requires careful management and is more complex to implement.
- 
- * **Chunking or Pagination:** If you're processing large datasets, process them in smaller chunks or pages to reduce the memory footprint at any given time.
- 
- * **Garbage Collection Tuning (Advanced):**  Tuning garbage collection settings can sometimes improve performance, but it's generally not recommended unless you're experienced with garbage collection and have profiled your application extensively.  Improper tuning can even worsen performance.
- 
- 
- **Example (Fixing a simple memory leak):**
- 
- ```java
- // Incorrect:  This leaks the connection!
- Connection dbConnection = DriverManager.getConnection(...);
- // ... do something with the connection ...
- 
- // Correct: Close the connection when done
- try (Connection dbConnection = DriverManager.getConnection(...)) {
-     // ... do something with the connection ...
- } catch (SQLException e) {
-     // Handle the exception appropriately
- }
- ```
- 
- Remember, increasing the heap size is usually a temporary solution.  The real fix lies in identifying and resolving the root cause of the excessive memory consumption.  Profiling tools are invaluable in this process.
